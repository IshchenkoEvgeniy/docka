# Формат данных проекта

Версия формата: **2** (`FORMAT_VERSION` в `src/core/model/project.ts`). Схемы — `src/core/model/*.ts` (zod);
всё, что читается с диска, проходит через них (`validate`).

## Папка проекта

```
МояИгра.doska/
  project.json                  id, начальное название, корневая доска, версия формата
  .stignore                     исключения Syncthing (не синхронизируется — у каждого устройства свой)
  data/
    <deviceId>/                 папка одного устройства — пишет только оно
      <docId>.snapshot          сжатое состояние документа Yjs (один кадр)
      <docId>.log               правки после снимка (кадры, только дописывается)
      device.json               имя устройства для окна синхронизации ({ "name", "at" })
  assets/                       картинки и файлы (шаг 3.6)
```

- `deviceId` — постоянный идентификатор устройства: латиница, цифры, дефис (`pc-home`, `phone`).
- `docId` — одна доска или общий документ проекта.
- Остальные папки и файлы в `data/` с недопустимыми именами игнорируются.
- `*.doska-tmp` — временные файлы атомарной записи (ADR 0002): живут доли секунды, не читаются и
  не синхронизируются.

## Папка проектов и файлы устройства

Проекты лежат подпапками `Название.doska` в «папке проектов» (её же добавляют в Syncthing).
По умолчанию на компьютере это `Документы/Доска`, на телефоне — папка данных приложения
(её не видит Syncthing). В настройках на телефоне кнопка «Разрешить доступ к файлам» выдаёт
разрешение «Доступ ко всем файлам» и переключает папку на общую `/storage/emulated/0/Doska` —
её и добавляют в Syncthing. На компьютере папку выбирают обычным диалогом. Смена папки
применяется перезапуском приложения.

Проект можно создать и в любой другой папке («Новый проект → Другая папка…») или добавить
уже существующий («Открыть проект из папки…»). Такие проекты запоминаются полным путём в
`projectPaths` и в избранном; из списка их можно убрать — файлы не трогаются. Для Syncthing
такую папку проекта добавляют отдельно. Имя папки получается из названия проекта:
без символов `<>:"/\|?*` и управляющих, при совпадении — «Название 2.doska». Дата изменения
проекта на главном экране — время самого нового файла внутри папки.

Настройки устройства — `settings.json` в папке настроек приложения, **не синхронизируются**:

| Поле | Что это |
| --- | --- |
| `version` | Версия файла настроек (1) |
| `deviceId` | Постоянный id устройства = имя его папки `data/<deviceId>/` во всех проектах |
| `deviceName` | Понятное имя («Компьютер», «Телефон») |
| `theme` | `system`, `light` или `dark` |
| `language` | Код языка интерфейса |
| `projectsFolder` | Своя папка проектов или `null` (по умолчанию) |
| `favorites` | Избранные доски: проект (id и папка), доска, запомненное название |
| `projectPaths` | Проекты вне папки проектов: полные пути папок `Название.doska` |

Битое поле заменяется значением по умолчанию, но `deviceId` сохраняется: иначе устройство
в проектах выглядело бы новым.

Рядом лежит `cameras.json` — масштаб и позиция досок на этом устройстве
(`"<projectId>/<boardId>": { offsetX, offsetY, zoom, at }`, 300 последних). Он тоже не
синхронизируется: у телефона и компьютера разные экраны.

## Кадр

И снимок, и журнал состоят из кадров:

| Смещение | Размер | Содержимое |
| --- | --- | --- |
| 0 | 4 байта | длина данных, uint32 little-endian (не больше 64 МБ) |
| 4 | 4 байта | CRC-32 (IEEE) данных, uint32 little-endian |
| 8 | длина | update Yjs (`Y.encodeStateAsUpdate` / `Y.mergeUpdates`) |

Чтение идёт до первого кадра, который не помещается в файл или не сходится по CRC; всё после
него считается повреждённым хвостом и не применяется.

## Правила записи

1. Своё устройство дописывает накопленные правки в свой `.log` одним кадром (`flush`).
2. Когда свой журнал больше порога (по умолчанию 1 МБ), всё состояние документа атомарно
   записывается в свой `.snapshot`, затем свой `.log` атомарно заменяется пустым.
   Сбой между этими шагами безопасен: правки окажутся и в снимке, и в журнале, Yjs не задвоит.
3. Если при открытии свой журнал оказался с повреждённым хвостом, он сразу сжимается — иначе
   новые кадры встали бы после мусора и не читались бы.
4. Файлы других устройств только читаются (при открытии и по `refresh`). Их повреждённые
   кадры пропускаются, о них сообщается в отчёте, приложение не падает.
5. Правки, прочитанные с диска, не записываются в свой журнал повторно.

## Почему так

Syncthing копирует файлы целиком и создаёт `.sync-conflict`, если один файл изменили на двух
устройствах. Здесь у каждого файла ровно один писатель, поэтому конфликтов файлов не бывает,
а слияние содержимого делает Yjs (CRDT). Проверено тестами `src/data/*.test.ts`, включая
случайные правки трёх устройств с синхронизацией в произвольном порядке.

## Модель данных

Все id — строки 8–64 символа из `A–Z a–z 0–9 _ -` (новые — 16 случайных символов).
Время — миллисекунды с 1970-01-01 UTC. Цвета хранятся именем палитры (`default`, `yellow`,
`orange`, `red`, `pink`, `purple`, `blue`, `teal`, `green`, `gray`); оттенок для темы — токен
`--color-card-<имя>`.

| Сущность | Поля | Где живёт |
| --- | --- | --- |
| Проект | `formatVersion`, `id`, `name`, `rootBoardId`, `createdAt` | `project.json` |
| Доска | `id`, `title`, `parentId` (null у корня), `icon`, `color`, `background` (`plain`/`dots`/`grid`), `createdAt`, `updatedAt`, `deletedAt` | документ проекта |
| Тег | `id`, `name` (вложенность через «/»), `color` | документ проекта |
| Элемент | `id`, `boardId`, `type`, `x`, `y`, `width`, `height`, `z`, `parentId` (колонка), `color`, `locked`, `tagIds`, `createdAt`, `updatedAt`, `deletedAt`, `data` | документ доски |
| Связь (стрелка) | `id`, `boardId`, `from`, `to` (элемент + сторона или точка), `label`, `color`, `lineStyle`, `startMarker`, `endMarker`, `deletedAt` | документ доски |
| Тип сущностей | `id`, `name`, `builtin`, `icon`, `color`, `fields` (по id поля), `createdAt`, `updatedAt`, `deletedAt` | документ проекта |
| Сущность | `id`, `typeId`, `name`, `values` (по id поля), `texts` (длинный текст), `createdAt`, `updatedAt`, `deletedAt` | документ проекта |

- Координаты и размеры элемента — в мировых единицах холста; `height` — последняя известная
  высота (нужна для отсечения невидимого и обзора, ADR 0001).
- Порядок наложения — по `z`, при равенстве по `id`: одинаков на всех устройствах.
- `data` — поля конкретного типа элемента; их схему задаёт определение элемента в `src/elements/`.
- Дерево досок не может содержать циклов (`wouldCreateCycle`); если цикл всё же пришёл из
  повреждённых данных, путь до доски обрывается, а не зацикливается.

## Раскладка по Yjs-документам

| Документ (`docId`) | Корневые карты Yjs | Что внутри |
| --- | --- | --- |
| `project` | `meta` | `name` — текущее название проекта |
| | `boards` | id доски → запись доски |
| | `tags` | id тега → запись тега |
| | `entityTypes` | id типа сущностей → запись типа |
| | `entities` | id сущности → запись сущности |
| `<id доски>` | `elements` | id элемента → запись элемента |
| | `connections` | id связи → запись связи |

- Запись — `Y.Map` с полями. Вложенные объекты (например, `data` элемента) — вложенные `Y.Map`,
  поэтому правки разных полей с разных устройств сливаются. Массивы (`tagIds`) и примитивы
  хранятся значениями: при одновременной правке побеждает последняя.
- При чтении каждая запись проверяется схемой; не прошедшие проверку пропускаются и
  перечисляются в отчёте (`readCollection`), остальные работают.
- `project.json` пишется один раз при создании и дальше не меняется (иначе два устройства
  без связи создали бы конфликт файла в Syncthing). Переименование проекта пишется в
  `meta.name` документа проекта; до первого переименования используется имя из `project.json`.
- Проект из более новой версии формата не открывается (и не изменяется) — приложение
  просит обновиться. Миграции старых версий — раздел «Версии и миграции».
- Документы досок загружаются при первом открытии доски, а не при открытии проекта.
- `.stignore`: при каждом открытии проверяется строка `*.doska-tmp`; строки пользователя
  сохраняются.

## Текст элементов

У заметки и заголовка в записи элемента есть поле `text` — `Y.XmlFragment` в раскладке
y-prosemirror: узлы `paragraph`, `heading` (атрибут `level`), `bulletList`, `orderedList`,
`listItem`, `blockquote`, `hardBreak`, `horizontalRule`; пометки текста `bold`, `italic`,
`strike`, `underline`, `code`, `link` (`href`). Фрагмент создаётся вместе с элементом.
У заметок этапа 2 текста в Yjs нет — есть `data.text`; Yjs-текст им создаётся при первой правке.
Подробности и причины — ADR 0003.

## Сущности (ADR 0004)

Сущность хранится в документе проекта один раз; на досках лежат её представления — элементы
типа `entity` с `data = { entityId, view }` (`view`: `chip`, `card`, `full`). Размер, место и
вид — у каждого элемента свои.

**Поле типа** (`fields.<id>`): `name`, `builtin` (ключ встроенного или null), `kind`, `order`,
`onCard` (показывать на карточке), `deletedAt` (скрыто), у списков — `options`
(`<id> → { name, builtin, order, color, removed? }`), у связей — `target` (id типа или null —
любой), `multiple`, `backName` (подпись обратного списка). Вид поля после создания не меняется.

| Вид (`kind`) | Значение в `values.<id поля>` |
| --- | --- |
| `text`, `url` | строка (до 2000 символов) |
| `longText` | не в `values`: `Y.XmlFragment` в `texts.<id поля>` (как текст заметки) |
| `number` | число |
| `boolean` | `true` / `false` |
| `select` | id варианта |
| `multiSelect` | объект `id варианта → true/false` |
| `image` | имя файла в `assets/` |
| `date` | строка `ГГГГ-ММ-ДД` |
| `relation` | id сущности; при `multiple` — объект `id сущности → true/false` |

- `null` — значение очищено. Значение не того вида не показывается, но и не стирается.
- Множества — объекты, а не массивы: отметки с разных устройств сливаются. Пустые множества и
  тексты создаются вместе с сущностью и при добавлении поля во все сущности типа — иначе два
  устройства создали бы их одновременно, и Yjs оставил бы одно.
- Обратные связи («НПС здесь») не хранятся — вычисляются по полям-связям.
- Встроенные типы «НПС», «Локация», «Предмет» имеют постоянные id (`builtin-npc`,
  `builtin-location`, `builtin-item`) и пустые названия с ключом `builtin`: текст берётся из
  перевода, пока пользователь не переименует.
- Упоминание в любом тексте — узел `mention` с атрибутами `id` (сущность) и `label` (название на
  момент вставки, запасной текст).

## Корзина

- Удаление мягкое: в записи ставится `deletedAt` (момент удаления), сама запись остаётся.
  Восстановление — `deletedAt = null`. Правки, сделанные на другом устройстве, пока запись лежала
  в корзине, не теряются.
- Вместе с элементом удаляется содержимое колонки и привязанные стрелки — с тем же `deletedAt`;
  восстановление возвращает то, что было удалено в тот же момент.
- Доска в корзине скрывает все вложенные доски. Восстановленная доска, родитель которой всё ещё
  в корзине, переносится в корень.
- Через 30 дней (`TRASH_RETENTION_MS`) записи удаляются окончательно: доски — при открытии
  проекта (вместе с вложенными и файлами своего устройства), элементы и стрелки — при открытии
  доски. Окончательное удаление записывается в журнал и не отменяется «Отменить».
- Теги удаляются сразу, без корзины (обычной отменой — можно вернуть).
- Сущности и типы удаляются в корзину (`deletedAt`); тип — только без живых сущностей.
  Через 30 дней при открытии проекта удаляются сущности, типы без сущностей (даже в корзине) и
  скрытые поля — вместе со своими значениями и текстами у всех сущностей типа.

## Резервные копии

- Раз в сутки (по UTC) — полное состояние проекта со всех устройств в один файл
  `<папка данных приложения>/backups/<id проекта>/<ГГГГ-ММ-ДД>.doskabackup`, вне синхронизации.
  Хранятся последние 14.
- Формат файла — кадры как у журнала: заголовок JSON
  (`kind: doska-backup`, `version: 1`, `createdAt`, `meta` из project.json, `docs`), затем пары
  кадров «id документа (UTF-8) — состояние Yjs».
- Восстановление — только в пустую папку: пишется project.json и снимки документов в папку
  восстанавливающего устройства.

## Версии и миграции

- Версия формата — в `project.json` (`formatVersion`) и в каждом Yjs-документе: карта `format`
  с отметками `v1`, `v2`… Версия документа — наибольшая отметка. Отдельные отметки, а не одно
  поле: при слиянии правок двух устройств версия только растёт и не может «откатиться».
- Миграции — `src/data/migrations.ts` (`MIGRATIONS`): по одной на каждую версию от 2, без
  пропусков (проверяется `checkMigrationChain` до любых изменений на диске).
- При открытии проекта: `project.json` приводится к текущей версии и переписывается — это
  единственный случай, когда он меняется после создания; документ проекта мигрирует сразу,
  документы досок — при открытии доски.
- Миграция документа обязана быть идемпотентной: два устройства могут выполнить её одновременно,
  Yjs сольёт результаты. Транзакция миграции записывается в журнал и не отменяется «Отменить».
- Документ или `project.json` новее приложения не открывается и не изменяется. Это касается и
  случая, когда Syncthing привёз обновлённую доску раньше обновлённого `project.json`.
- **Формат 2** (этап 4): в документе проекта карты `entityTypes` и `entities`; миграция создаёт
  встроенные типы, если их нет (время создания 0 — у двух устройств записи одинаковы).
  Новые проекты получают их той же миграцией при первом открытии.
- Как добавить версию: поднять `FORMAT_VERSION`, добавить миграцию в `MIGRATIONS`, тест на неё
  (старый проект → новый) и описать изменение здесь.
