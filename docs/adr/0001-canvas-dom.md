# 0001. Холст: DOM для детального вида, один canvas для обзора

Дата: 2026-10-31 · Статус: принято

## Контекст

Карточки содержат живой текст (заметки, таблицы, редактор TipTap), поэтому ТЗ выбирает
DOM-холст: элементы — обычные HTML-блоки, камера — один CSS `transform` на слое.
Требование (ТЗ, раздел 10): 60 FPS при пане и зуме на 1000 элементах (ПК) и 300 (телефон).

## Замер прототипа (шаг 0.4)

Сценарий `Автозамер (6 секунд)`: 2 с пан при 100 %, 2 с зум 30–200 %, 2 с обзор всей доски.
1000 карточек с заголовком и 1–3 строками текста, окно 1280×800.

Среда ИИ: headless Chromium **без видеокарты** (программная отрисовка, 2 ядра CPU) —
это заметно хуже реального устройства, цифры нужны для сравнения вариантов, не как итог.

| Вариант | Пан 100 % | Зум 30–200 % | Обзор доски |
| --- | --- | --- | --- |
| Все 1000 карточек в DOM | 15 FPS | 13 FPS | 11 FPS |
| Виртуализация (35 карточек в DOM при 100 %) | **60 FPS** | 47 FPS | 11 FPS |
| + упрощённый DOM-вид при масштабе < 40 % | **60 FPS** | 51 FPS | 13 FPS |
| + обзор одним `<canvas>` при масштабе < 50 %, запас 25 % | **60 FPS** | **59 FPS** (1% low 60) | **60 FPS** |
| Для сравнения: 100 карточек без оптимизаций | 60 FPS | 60 FPS | 60 FPS |

Замеры на устройствах пользователя (заполнить после запуска `pnpm tauri dev` → кнопка «Автозамер»):

| Устройство | Всего | Пан | Зум | Обзор |
| --- | --- | --- | --- | --- |
| ПК (Windows, WebView2, 144 Гц), упрощённый DOM-вид | 93 (1% low 18) | 142 | 119 (1% low 29, худший кадр 118 мс) | **18** |
| ПК, обзор одним `<canvas>` | 117 (1% low 48) | 143 (1% low 141) | 132 (1% low 71, худший кадр 70 мс) | **76** (1% low 48) |

## Решение

1. Камера: transform слоя меняется напрямую в `requestAnimationFrame`, минуя React
   (`canvas/useCameraControls.ts`).
2. Виртуализация: рендерятся только элементы в видимой области плюс половина экрана с каждой
   стороны. Область пересчитывается, только когда экран вышел за запас или масштаб сильно
   изменился (`canvas/visibility.ts`, `useRenderRect`) — во время пана React не перерисовывает.
3. Обзор: при масштабе < 50 % (с зазором ±3 %, чтобы вид не мигал на границе) DOM-элементы
   не рендерятся вовсе, а все элементы рисуются одной картинкой на `<canvas>`
   (`canvas/overview.ts`, `OverviewCanvas`): прямоугольники, сгруппированные по цвету, —
   один вызов отрисовки на цвет. Замер на ПК пользователя показал, что 1000 упрощённых
   DOM-блоков дают 18 FPS даже на реальном железе, поэтому запасной план стал основным.
4. Каждый тип элемента отдаёт для обзора прямоугольник и цвет (токен темы).

## Альтернативы

- **Canvas 2D / WebGL для всего холста** (как Figma, tldraw частично): быстрее на обзоре,
  но текст, выделение, редактирование и доступность пришлось бы писать заново. Отклонено.
- **Упрощённый DOM-вид на мелком масштабе** (без текста, один блок на карточку): проверен,
  на ПК даёт 18 FPS на обзоре 1000 карточек. Отклонён в пользу canvas.

## Последствия

- Все элементы обязаны иметь известные габариты (x, y, ширина, высота) — нужны для отсечения.
- Каждый тип элемента описывает свой вид в обзоре (прямоугольник и цвет; позже — миниатюра
  картинки, заголовок крупным шрифтом).
- Выделение и наведение на мелком масштабе будут считаться по геометрии, а не по DOM.
- Открытые вопросы для шага 2.2:
  - обзор перерисовывает все прямоугольники каждый кадр (76 FPS, 1% low 48 на ПК) — при пане
    можно сдвигать готовую картинку и перерисовывать только при смене масштаба;
  - единичные кадры до 70 мс на ПК и до 280 мс на телефоне, когда в DOM разом добавляется
    много карточек с текстом (переход через порог 50 %, пересчёт области при пане; на узком
    экране телефона запас в 25 % — всего ~90 px) — монтировать порциями по бюджету кадра
    и задавать запас не меньше фиксированного числа пикселей;
  - резкость текста сразу после зума при `will-change: transform`.
